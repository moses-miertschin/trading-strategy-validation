# How correctness was enforced

Written for an engineer who has never seen a backtest. You do not need to know
what a Sharpe ratio is to read this.

**The problem.** A backtest is a program whose output is a number nobody can
independently check. If it says 1.11 and the truth is 0.46, nothing crashes, no
test goes red, and the number goes into a report. Ordinary testing does not help
much: the function returns *a* float, the types are right, the code runs. Every
defect in this project's history was a silent numeric change.

So the question I actually had to solve was not "does the code work" but **"how
would I find out if it didn't?"** Five mechanisms, each with the specific defect
behind it — which in two cases is the defect that caused the mechanism to exist
rather than one it caught.

---

## 1. Mutation testing as a hard gate

**The rule:** every new automated check must be *demonstrated failing* under a
deliberate perturbation before it is committed, and the perturbation recorded in
the commit message. A check that has never been observed to fail is not evidence;
it is decoration.

**Why the rule exists.** On 2026-08-02 I wrote five regression checks. All five
were incapable of failing. The worst shipped as a regex pattern beginning with a
literal **backspace byte** — it matched nothing, passed vacuously, and carried a
failure message describing a real defect, so the suite reported green while
asserting nothing. **All five were found by adversarial review. None was found by
the suite.** The root cause was mundane: the checks had been authored through a
shell heredoc, which collapsed escape sequences into control bytes.

The catalogue of shapes that cannot fail is now written down, because each has
happened here: asserting something true by definition; computing one value,
interpolating it into the failure message, and asserting a *different* one;
comparing a column against another column derived from it; checking a value is
*present* rather than *correct*; and a pattern containing a control byte.

**The gate is a program.** `tools/mutate.py` takes a registered perturbation —
a named before/after edit to a specific line — applies it, runs the suite,
restores the file, and verifies the restore was byte-exact. If the suite still
passes, it prints:

```
*** THIS CHECK CANNOT FAIL -- it is decoration ***
```

and fails the run. It also reports which passing checks no perturbation ever
broke, so undemonstrated checks are visible rather than assumed fine.

**146 registered perturbations** across three suites. Measured coverage on
2026-08-13: `ops` 61 of 61 checks demonstrated failing, `followups` 142 of 143,
driver 4 of 4.

**Checks get deleted, not kept.** This is the part that matters. A check written
to confirm the ops test suite never polluted the real audit log read, in full:

```python
os.path.isfile(real_log) == os.path.isfile(real_log)
```

True by definition. It was **deleted rather than repaired**, with the reasoning
left in place so nobody rewrites it, because a redundant check is not worth
repairing. On 2026-08-12 I deleted a second one of my own before committing — an
assertion that two sets formed a disjoint cover, when the function under test
built them by partitioning on a predicate, so disjointness and coverage were
arithmetic identities.

**The gate catches bad perturbations too, and that is the most convincing thing
I can say about it.** On
2026-08-12 I wrote a perturbation intended to make a check fail by widening a
directory scan to include a directory it should ignore. The driver reported
`fails=0` — decoration. The perturbation had widened the scan but left a
downstream filter intact, so the injected value was admitted and dropped one line
later. **The check was fine; my attempt to break it was not**, and the tool said
so before it reached a commit.

**The honest limit:** the 146 perturbations cover the `ops`, `followups` and
driver suites. The 340-check regression suite is not in a registered perturbation
set. What is true is that every check added since the rule was adopted was
demonstrated failing before commit — not that all 548 checks have a live
perturbation today.

## 2. The reproducibility sweep: byte-level artifact comparison

Every published measurement **in `trading-research/`** lives in a Markdown report
generated by a script. That scope is doing real work: the review documents, the
handoffs, and the `ops/` analyses quoted elsewhere in this write-up are
hand-written, publish measurements of their own, and sit outside the swept
directories entirely. **The sweep re-runs each
generating script with no environment variables
set, compares the committed artifact against what the script just produced byte
for byte, and restores the tree.**

**What this catches that a unit test cannot.** A unit test asserts that a function
returns the right value. It cannot notice that the *committed document* contains a
sentence no code in the repository emits. On 2026-07-31 the sweep found **eight
artifacts carrying prose their generator never wrote** — hand edits that had
accumulated behind a rule forbidding them. Re-running the backtest would have
silently destroyed them, and one of them was a bug-fix notice.

One more class it was built *because of*, and one it caught. Both are invisible
to any test of the code in isolation.

- **Built because of: a published report generated under settings the script does
  not default to.** One report had been produced with an environment variable
  raising a permutation count from 5,000 to 10,000. A plain re-run silently
  restated its statistics; nothing errored, the numbers just quietly changed.
  **The sweep did not find this — it exists because of it**, and its own report
  says so in the header: *"That was found by accident. This sweep looks for the
  rest on purpose."* The fix became a rule: a tunable knob's default is the value
  the record was made at, never a faster development value passed in by hand.
- **Caught: a published script that could not run at all.** `pipeline_detection_floor.py`
  was the record of a headline figure. A change elsewhere moved a default it
  inherited, it measured 13 windows instead of 14, and its own internal assertion
  aborted every run. **It sat broken for five days**, because the only sweep run
  routinely was the fast one that skipped it.

**The current record.** 86 scripts, 7 excluded (they need network access), **79
runnable and all with a verdict**: 66 byte-identical, 12 differing only in an
embedded timestamp with every number identical, and **1 genuine difference with a
written and classified cause**. Zero timeouts, zero errors. The run took **502.5
minutes**.

**Re-run end to end on 2026-08-13 after the harness changed, and every one of the 86 verdicts came back identical.** That is the strongest single piece of evidence in this document: the record is not a story about one lucky afternoon.

The one difference is a script that seeds a random number generator from a
per-process hash, so it cannot reproduce itself. That is recorded as a known
non-deterministic cause rather than quietly excluded — and it is why one
withdrawn claim in this repository is still an open debt: fixing the artifact
would move fourteen published numbers, and that is a decision, not a task.

## 3. Phase gates: authorization as a file

Five phases, from research to live trading. **Advancing requires a written
approval note in `docs/phase-gates.md` before any work happens.** The gate is a
file in version control, not a judgement call at the keyboard.

**No strategy ever advanced past Phase 3.** Phase 3 *was* authorized in writing —
`docs/phase-gates.md` carries **four dated grants** (2026-07-05, 2026-07-06,
2026-07-30, and a conditional one of 2026-07-30/31) across nine `## Phase 3`
sections, which is the mechanism working as designed.
**Phase 4 authorization was never granted and never requested**, and every closed
cycle records Phase 4 eligibility as `BLOCKED`. No broker connection, API key,
`.env`, order-execution code, paper trading or live trading has ever existed here.

> **This was a defect in four *sources*, not only in this write-up, and it is now
> fixed.** `Closing_Statement_2026-08-05.md`, `Project_Capstone_2026-08-03.md`,
> `Verdict_Which_Ending_2026-08-03.md` and `SESSION_HANDOFF.md` all stated that
> Phase 3 authorization *"was never granted"*. **All four are corrected in place
> as of 2026-08-12**, each carrying a dated correction note rather than a silent
> rewrite. None is a generated artifact, so no regeneration was needed.
>
> The sentence mattered because it described the phase gate **as having been
> bypassed** — the opposite of what happened. Advancing *to* Phase 3 required a
> written note and got one, four times; advancing *past* it never happened.

For an engineer the interesting property is that this is a *precommitment
mechanism*, **and the first time it was put under real pressure it was overrun.**
The rule that came out of that is worth stating: **capability is not
authorization.** On one run an authorization
named a single file; a defect was then found spanning four documents. Three were
fixed — the authorized one, and two more that happened to be easy; the fourth was
generated and was recorded as a debt. The boundary
that actually operated was "what could I repair", not "what was I allowed to
repair". That overrun was disclosed at the top of the verdict rather than in a
footnote, and the corollary written down: **authorize a claim or an outcome, not a
file**, because a file-scoped authorization becomes wrong the moment the defect
turns out to be bigger than the author knew.

## 4. Adversarial review as standing practice

After most work sessions a reviewer was spawned with one instruction: **refute,
do not confirm.** A review returning "looks good" was treated as a failed review.

**The reviewer was a separate AI agent instance, not a person**, briefed
read-only and pointed at named error classes. That is worth saying plainly
because it changes what the practice is evidence of: it is cheap, it is
repeatable, and it is **not** independent in the way a second engineer would be.
What makes it load-bearing is the second half — **every finding was independently
re-verified by me**, re-running the computation or reading the code, before being
accepted or rejected. Findings were
rejected: one round returned 12 and 2 did not survive verification.

**At least nine rounds ran.** Representative tallies: 20 findings all confirmed
(2026-08-03), 14 findings with 13 confirmed and 1 rejected (2026-08-04), 9 with
7 confirmed and 2 cleared (2026-08-07), 16 all confirmed (2026-08-12).

**The uncomfortable part, and the reason it earns its place here: review
repeatedly overturned conclusions I had written hours earlier the same day.**
Findings concerning work done that same session: **3 of 7** on 2026-08-06,
**4 of 8** on 2026-08-07, **12 of 16** on 2026-08-12.

Three concrete overturns:

- I wrote that a fix made tampering with the record *"require forging the record
  itself — a much larger and far more visible act… the strongest property
  available."* Review measured it. **The actual cost of defeating it was one blank
  line appended to a file.** The mechanism was real; my characterisation of its
  strength was not measured and was wrong.
- A function meant to find the commit carrying a record used `git log -1 -- <path>`,
  which returns the commit that most recently **touched** the path — *including
  the commit that deleted it*. The guard printed `anchor VERIFIED` about a commit
  where the record does not exist. **The word "touched" had stood in for
  "carries"**, inside a fix written to close exactly that class of defect.
- On 2026-08-12 I claimed a data anomaly reproduced *"exactly the same seven
  bars"* across two independent fetches. Review checked all eight instruments
  rather than the four I had looked at. **There were ten, across six instruments** —
  I had checked only the ones already known to be affected, found what I expected,
  and stopped.

None of these was caught by a test. All three were caught by someone being paid,
in effect, to disagree.

## 5. Tagging conditions: what makes a record trustworthy

A release tag on this project asserts something narrow and checkable: **the
integrity of the record, not the correctness of its conclusions.** Six conditions,
each decidable from committed files with no appeal to anyone's recollection.

| | Condition |
|---|---|
| N1 | every script in the swept directories is covered, and any gap is named |
| N2 | no verdict is absent — zero timeouts, errors, contaminations, unrun scripts |
| N3 | every genuine difference carries a written, classified cause |
| N4 | the record was produced by *this tree's* verdict logic |
| N5 | the suite passes, and no artifact still asserts a claim the project withdrew |
| N6 | no swept script has drifted since the record was made |

**They were rewritten once, and why is the interesting part.** The original five
were written, in the author's own words, to answer *"did the sweep finish?"*:

> *"It has finished. They do not answer the question that matters now, which is
> **is the sweep's verdict trustworthy?**"*

The rewrite was driven by a specific defect. **13 of 77 verdicts had been produced
by a keyword filter and were then quoted as though a numeric comparison had
produced them.** Nothing anywhere checked that the record and the checking code
were the same generation. That is what N4 exists for: the sweep stamps a
fingerprint of its own verdict logic into the report it writes, and the check
recomputes that fingerprint from the tree and requires equality. It fails
precisely when verdicts start meaning something other than what they say.

The fingerprint currently covers 17 verdict-deciding functions, eight of the
module's registries, the swept-directory list and the per-script timeout.
**`DIFFERS_EXPLAINED` is a registry and is not among them** — a gap I found while
checking this sentence, not one the record already named. Its value is
`5f1d86106dca75dd`. If any of those change without the sweep being re-run, N4
fails and tells you the record is stale — **and that is the only sanctioned reason
to spend 8.4 hours re-running it.**

Two properties worth noting. First, the old conditions included *"the report has
been read by a human"*, which was dropped because it is **not checkable from
committed evidence** — it is a claim about someone's attention.

Second, **the fingerprint's first version had a defect that its own instability
made obvious.** It hashed Python sets directly, and `repr()` of a set iterates in
hash order, which CPython randomises per process — so the fingerprint **differed
between runs on an unchanged tree**. Nothing detected that; *I* noticed the value
would not sit still, which is a person reading output, not a system catching
something. A check that fails at random is worse than no check. Every registry is now
canonicalised with `sorted()` before hashing.

**A known limitation, since this section is about trusting the record.** N4 reads
the per-script timeout from the environment of whoever runs the suite, so an
unrelated environment variable set in that shell makes N4 fail on an untouched
tree. That is a false alarm rather than a false pass — the safe direction — but it
is a real defect, it is recorded as open, and fixing it requires re-running the
8.4-hour sweep.

## What this adds up to

Four suites, **548 checks**. 146 perturbations, demonstrating that **207 of the
208 checks** in three of those four suites can actually fail — 61 of 61, 142 of
143, and 4 of 4.

**They are not all passing as I write this, and that is the system working.** One
check is red: N4, which asserts that the committed reproducibility record was
produced by *this* tree's verdict logic. Two fixes on 2026-08-12 changed that
logic, so the assertion is false until a fresh sweep regenerates the record. The
alternative — updating the recorded fingerprint to match — would make the check
green by telling it to expect what it found, which is the one thing it exists to
prevent. A generated record that re-derives
from its own scripts. Six mechanical conditions on whether that record can be
trusted. At least nine rounds of review briefed to attack it.

**None of that made the strategies work.** It is what made the finding that they
could not be validated something I am willing to put my name to — and, more to the
point, it is what repeatedly stopped me from publishing something better-sounding
and wrong.
